# 新旧系统功能复刻验证方案设计

> 验证对象：新版 `single-kotlin`（Kotlin + MVVM）vs 旧版（Java + MVP）
> 目标：证明新版完整复刻旧版业务功能；第一步内部自证（快速定位差异），第二步交付证据报告
> 状态：设计已确认，待评审

## 1. 背景与目标

团队正在用 Kotlin + MVVM 重写 Java + MVP 的电视盒子 App。重写完成后需要回答一个核心问题：**新版是否完整复刻了旧版的业务功能**。

本方案把 docs/ 下现有人工形式的「新旧 XX 功能对比审查报告」系统化为**可重复的自动化验证闭环**：

- 旧版实跑录制业务路径，作为功能基线；
- 新版实跑同一路径，自动对比接口行为差异；
- 输出按功能维度组织的差异报告，快速定位「哪个功能没复刻、哪里不一致」。

第一步服务研发组内部验收（重效率、快速定位）；第二步把结果升级为交付给领导/客户的正式证据（覆盖率结论 + 差异清单）。

## 2. 总体流程

五步闭环，全程使用**同一台盒子、同一网络环境**录制两遍（消除设备与网络差异对对比的干扰）：

```text
旧版实跑录制 → AI 生成功能矩阵草稿 → 人工校正矩阵 → 新版实跑录制 → 自动对比 → 差异报告
```

1. **旧版实跑录制**：测试同事在旧版 App 上按既定路径完整操作一遍，录制全部 HTTP 请求/响应（含时间戳、请求体、响应体），叠加 logcat / console 日志；
2. **AI 生成矩阵草稿**：AI 基于录制数据自动切分按钮级操作步骤、命名功能条目、关联触发接口，产出矩阵草稿（JSON）；
3. **人工校正矩阵**：人快速过一遍，修正命名与接口归属，矩阵纳入版本管理；
4. **新版实跑录制**：同一盒子上，新版 App 按同一路径操作一遍（不要求顺序与旧版完全一致，按接口对齐）；
5. **自动对比**：按 method+path 对齐两个目录的录制数据，输出按功能维度组织的差异报告。

## 3. 功能矩阵（核心数据模型）

功能矩阵是「完整」二字的度量基准：没有它，只能证明「跑过的接口一致」，无法回答「完整复刻」。

### 3.1 结构

```text
模块 → 功能条目 → 按钮级操作步骤 → 触发接口集
```

- **按钮级操作步骤**：用户操作的粒度，例如「首页 → 点击搜索框 → 输入关键词 → 点击搜索按钮」；每个步骤关联其触发的接口；
- **接口条目**：method + path + 请求特征（关键 header / body 结构），用于新版对齐；
- **矩阵文件**：JSON，纳入 git 版本管理，是验证的度量基准和最终证据的一部分。

### 3.2 数据模型示例

```json
{
  "module": "首页",
  "entries": [
    {
      "id": "home-search",
      "name": "搜索流程",
      "steps": [
        { "action": "点击搜索框", "apis": [{ "method": "GET", "path": "/api/search/hot" }] },
        {
          "action": "点击搜索按钮",
          "apis": [{ "method": "POST", "path": "/api/search/query" }]
        }
      ]
    }
  ]
}
```

### 3.3 构建方式（AI 草稿 + 人工校正，先 A 后 B）

- **输入**：旧版实跑录制的请求序列（时间、URL、方法、请求/响应体）+ logcat / console 日志；
- **AI 环节**：独立组件（LLM 处理导出的结构化录制数据），负责切分按钮级步骤、命名功能条目、关联接口，输出矩阵草稿；
- **人工校正**：直接编辑矩阵 JSON（无需专门 UI），修正 AI 的命名与归属错误；
- **演进**：先 A（草稿 + 人工校正，人工把关质量），积累多轮样本验证 AI 准确率后，逐步过渡到 B（AI 全自动）。

## 4. 对比引擎

### 4.1 对齐规则

- 主键：method + path（忽略 query，沿用 tape 既有语义）；
- 两遍录制不要求操作顺序一致，按接口主键对齐；
- 环境约束：两遍录制必须同一台盒子、同一网络环境（用户确认），降低动态差异。

### 4.2 差异三分类

- **缺失**：旧版矩阵中有、新版未调用（该功能未复刻或未跑到）；
- **新增**：新版多出的接口（行为扩展或异常请求）；
- **变更**：同一接口的状态码 / 响应头 / 响应体有差异。

### 4.3 忽略规则（防假差异）

- 按字段路径忽略动态值（time / token / id / 随机数等），规则可配置；
- 未被规则覆盖的差异标记为「疑似动态，待人工确认」，不直接判失败。

### 4.4 对比维度

- 状态码；
- 响应头（关键头，如 content-type）；
- 响应体：JSON 语义 diff（字段新增 / 删除 / 值变化）；
- 耗时：提示级（不判失败）；
- 请求体差异单独列出：用于定位「是新版发错请求，还是服务端行为变了」。

## 5. 报告

### 5.1 内部报告（第一步）

按功能条目汇总：

- 全部一致；
- 部分变更（列出具体字段差异）；
- 接口缺失（对应功能条目标红）。

输出形态：终端摘要 + Markdown 报告（可与现有「新旧 XX 功能对比审查报告」衔接，作为审查的输入/佐证）。

### 5.2 交付证据（第二步）

- 覆盖率结论：矩阵条目验证比例、未验证条目**显式列出**；
- 差异清单 + 结论模板；
- 原则：**未覆盖的功能条目必须显式列出，不允许默认声称完整**。

## 6. 工具承载

| 环节 | 工具 | 说明 |
| --- | --- | --- |
| 录制 | tape record（现有） | 快照目录即录制产物 |
| 对比 | tape compare（新增） | 读两个录制目录 + 矩阵 + 忽略规则 → 差异报告 |
| 矩阵生成 | AI 独立脚本 | 输入录制导出数据 → 输出矩阵草稿 |
| 人工校正 | 直接编辑 JSON | 矩阵变更入 git |

## 7. 错误处理与边界

- **旧版已无法运行**：没有基线可录，本方案不成立；设计上保留「接口文档导入建基线」的扩展位；
- **动态值噪音**：忽略规则兜底；未覆盖差异标「疑似动态，待人工确认」；
- **新版漏接口**：对应功能条目标红，报告显式提示「该功能未验证到接口」；
- **录制覆盖不完整**：矩阵只包含实跑覆盖的接口，报告如实反映覆盖率，不虚报；
- **UI / 交互层**：本方案只覆盖接口行为层；页面跳转、客户端状态等不体现在 HTTP 上的行为不在第一版范围（后续可叠加截图对比 / UI 自动化，独立立项）。

## 附录：L2 业务流层设计（M2）

### 背景与定位

L1 接口契约对齐只能证明「API 层复刻」（没漏接口、结构一致），证明不了业务行为一致：接口返回相同，业务结果可能不同（如下单接口同样 200 但新版未真正扣款）。L2 把验证从「接口对齐」推进到「业务流对齐」，包含三块：**接口调用序列对齐、状态依赖对齐、业务结果断言**。

### L2-1 接口调用序列对齐

- 两遍录制各自完成 L1 配对后，按录制顺序比较配对接口的调用序列；
- 算法：最长公共子序列（LCS），容忍两遍操作顺序的微小差异（如用户点击节奏不同）；
- 输出：序列差异——新版新增 / 缺失 / 顺序反转的调用步骤；
- 示例：基线 `[登录, 取token, 下单, 查订单]`，新版 `[登录, 取token, 下单]` → 缺失「查订单」步骤，报告标出。

### L2-2 状态依赖对齐

- 定义：前序接口响应的关键字段（token / id / 签名）驱动后续请求参数；
- 验证策略：**不单独做值追踪**，作为 L1（请求指纹对齐）+ L2-1（序列对齐）的推论——两遍录制请求指纹一致且调用序列一致 ⇒ 状态传递链路一致；
- 例外标记：若序列一致但请求指纹不一致（参数值不同），报告标出「参数值差异」，人工确认是否为业务变化（如用户换了搜索词）。

### L2-3 业务结果断言

- 矩阵功能条目新增 `expected` 字段：JSONPath + 操作符断言列表；

```json
{
  "id": "home-search",
  "name": "搜索流程",
  "steps": [
    { "action": "点击搜索", "apis": [{ "method": "POST", "path": "/api/search/query" }] }
  ],
  "expected": [
    { "path": "$.data.list", "op": "nonEmpty", "desc": "搜索结果非空" },
    { "path": "$.errorCode", "op": "eq", "value": 0, "desc": "无错误码" }
  ]
}
```

- 操作符：`eq` / `exists` / `nonEmpty` / `gt` / `contains`；
- 对比时对匹配到的接口响应分别断言（基线与新版各执行一遍）：
  - ✅ 基线断言通过、新版断言通过 → 业务结果一致；
  - ❌ 新版断言失败 → **业务结果未复刻**（关键告警，独立于接口 diff 标红）。

### L2 报告扩展

新增「业务流验证」小节：

- 调用序列：一致 / 差异列表；
- 业务结果断言：逐功能条目 ✅ / ❌（断言失败与接口 diff 分开呈现）。

### L2 实现要点

- 序列对比：复用 L1 对齐结果，按录制 id 顺序排列配对项后做 LCS；
- 断言引擎：JSONPath 取值 + 操作符判定（复用 L1 的字段路径能力）；
- 矩阵模型：`MatrixEntry` 增加 `expected: Vec<Assertion>`（可选字段，向后兼容无断言的旧矩阵）；
- 报告：`render_report` 增加业务流小节。
